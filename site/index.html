Chapter 1

The problem

An eVTOL propulsion design — motor count, battery topology, redundancy scheme, cooling architecture — has to satisfy dozens of clauses scattered across EASA and FAA certification documents: SC-VTOL-01, CS-23, CS-27, SC E-19, AMC-20 series. A single missed clause, like a shared power bus quietly defeating a "triple redundant" flight computer, is exactly the kind of failure certification review exists to catch. The goal here is a system that reads a design description in plain engineering language and tells you, with an exact clause reference and quote, what it violates and how to fix it.

The obvious approach is retrieval-augmented generation: embed the regulatory documents into a vector store, embed the design description as a query, retrieve the nearest chunks, hand them to an LLM. That's where this project started. It's also where the first real problem showed up.

Chapter 2

Why plain vector search fails

Embedding-based retrieval works by compressing each chunk of text into a single vector before it ever sees a query, then ranking chunks by how close their vector sits to the query's vector. That works well when the query and the relevant text share vocabulary. It breaks down when the connection between them requires reasoning — inferring that a shared 28V bus across three "redundant" flight computers is, functionally, a single point of failure, even though the design description never uses the words "single failure" at all.

This is a known limitation of bi-encoder retrieval — the academic term is reasoning-intensive retrieval (see the BRIGHT benchmark and the ReasonIR paper). A bi-encoder has to commit to a chunk's vector before it has ever seen the query, so it can't do any inference at match time. It isn't a tuning problem; it's a structural limitation of the architecture.

Chapter 3

Fixing it with HyDE

HyDE (Hypothetical Document Embeddings) sidesteps the vocabulary gap by never embedding the raw query at all. Instead, an LLM is asked to write a short hypothetical regulation excerpt — in the actual register and terminology of an EASA/FAA document — that plausibly answers the query. That fabricated excerpt is what gets embedded and searched with, combined with three query rewrites and rank fusion across all variants.

The prompt deliberately does not hard-code "failure conditions" language — an earlier version was tuned to that one test case and got rewritten to infer the actual sub-domain (structural, battery/energy, EMI, redundancy, software assurance, operational) from the query itself, so it generalizes instead of overfitting to the example that motivated it.

Known unresolved issue

Repeated PDF running headers/footers were never stripped at extraction time, so 5–9 of every 20 retrieved chunks in some domains are near-duplicate header junk, not substantive text. HyDE fixed the vocabulary-gap problem; it didn't fix this separate extraction issue.

Chapter 4

The pivot: read everything instead

HyDE narrowed the gap but didn't close it — a meaningful fraction of relevant material still sat outside any retrieval cutoff. At this corpus's actual size (9 stage-1 documents, roughly 876K tokens total) a different question became worth testing directly: what if the model just reads every document in full, with no retrieval step at all, so nothing can be silently excluded by a ranking cutoff?

Three models were tested reading the full corpus unchunked on the same real design description — Kimi K3, Gemini 3.1 Pro, and DeepSeek V4 Flash — compared honestly on answer quality and cost, with no preference given going in. DeepSeek V4 Flash gave the strongest, most specific answer (correct clause, correct quote) at a small fraction of what the larger-context reads from the other two models cost. That made full-corpus reading the primary architecture for Stage 1 and Stage 2 here, with retrieval kept in reserve as a fallback for corpora too large to read whole.

Every model in this class occasionally burns its entire output budget on invisible chain-of-thought reasoning before writing a visible answer, returning nothing usable — a real failure mode hit more than once while building this, fixed with generous output budgets and retry-on-empty-response logic rather than assuming a response always arrives.

Chapter 5

Chunking done right (for retrieval mode)

Even with full-corpus reading as the default, the retrieval fallback still needs well-formed chunks. The naive approach — slice every document into fixed 1,200-character windows with 200-character overlap — is fast but blind: it cuts mid-sentence, mid-clause reference, even mid-table-row, with no regard for where the document's own structure actually breaks.

The reviewed boundaries come from sending each document's paragraphs to an LLM and asking it to propose semantically coherent cut points, validated in code afterward — every proposal is checked for full coverage with no gaps or overlaps and retried up to three times if the shape is wrong, which caught real silent failures (empty boundary lists, malformed JSON, duplicate indices) during development.

Chapter 6

The pipeline, as it runs today

Both stages follow the same shape: two small, cheap HyDE calls run in parallel and get combined, then one large call reads everything — both framings, the corpus, and the design or report — at once and reasons over it directly.

Does HyDE still earn its place once the model reads everything anyway?

Worth asking directly: once Stage 1 reads the full corpus instead of retrieving from it, is the HyDE call still doing anything, or is it a leftover from the retrieval-era architecture? Tested it directly — same design description, same corpus, same model, run three ways: with HyDE, with two independent HyDE framings combined, and with no HyDE at all.

With no HyDE, Stage 1 still caught every issue stated directly in the design description, but missed the issues that only emerge from connecting two separate parts of it — exactly the "reasoning-intensive" gap from Chapter 2, just showing up one stage later than expected. A single HyDE framing fixed that partially: whichever cross-cutting issue it happened to name, Stage 1 caught cleanly with a real clause citation — but it only ever named one, so the report was only ever strong on that one. Running two independent framings in parallel and combining them, which is what the pipeline does today, trades that single sharp catch for broader coverage of the straightforward issues, at the cost of neither cross-cutting finding coming through quite as cleanly on its own.

Honest limitation

This isn't a solved problem. HyDE's own output varies between runs on identical input, and whichever cross-cutting issue it happens to name is the one Stage 1 reliably elaborates on — the ones it doesn't name are the ones most likely to get missed or under-developed. Two framings broaden what gets named without guaranteeing every hard issue gets named clearly. HyDE measurably helps here; it doesn't yet catch everything, every time.
